2. 3D Tiles のバージョンとコンテンツ形式

推奨形式: 3D Tiles 1.1（.glb コンテンツ） — この環境（KASUGAI Canvas + CesiumJS 1.147）では glb を第一選択にしてください。自動変換タブの既定出力形式も glb (3D Tiles 1.1) に設定しています。理由は次のとおりです。

  • Canvas の全対応エンジン（Cesium ネイティブ 1.147 / deck.gl 系 / Navara）で表示できる
  • Draco / meshopt / KTX2 圧縮で転送量・デコード負荷が最小（＝表示が速い）
  • メッシュ・インスタンス・点群を 1 形式で統一でき、pnts 廃止後の 1.1 標準に沿う
  • mago 1.15.4 は既定で 1.1 出力のため、追加指定なしで glb が得られる

例外（1.0 を選ぶケース）: CesiumJS 1.107 未満の古いビューア・外部ツールへ配る場合や、 受け取り側が 1.0 のみ対応の場合。そのときは mago に --tilesVersion 1.0、 gocesiumtiler に --version 1.0、Py3DTiles に --spec-version 1.0 を指定し、 .b3dm / .pnts で出力します。

出力タイルセットの実バージョンは tileset.json の "asset": { "version": "…" } で確認できます。 コンテンツ形式と仕様バージョンは次のように対応します。

仕様コンテンツ形式特徴
3D Tiles 1.0 .b3dm / .i3dm / .pnts 従来のバイナリ形式。内部は glTF を包んだ独自コンテナ。CesiumJS をはじめ広く互換。
3D Tiles 1.1 .glb（glTF 直接コンテンツ） コンテナを廃し glTF をそのままコンテンツに使う。EXT_mesh_features / EXT_structural_metadata で属性・フィーチャ ID を保持。Draco 圧縮・KTX2 テクスチャ等 glTF 拡張の資産を直接利用でき、転送量・デコード負荷を最も削減できる。点群も glb で表現され pnts は不要になる。

2-1. コンテンツ形式別の特徴と速度

3D Tiles の LOD（レベル・オブ・ディテール）は、コンテンツ形式ではなく tileset.json のタイル木（各タイルの geometricError と refine）で管理されます。ビューアは画面上の誤差許容量に応じて 描画タイルを自動切替えするため、全形式が等しく「距離に応じた描画軽量化」の恩恵を受けます。 そのうえでの形式ごとの速度特性は次のとおりです。

形式用途LOD の仕組み速度面の特徴Cesium 対応
.b3dm 建物・構造物などバッチ化したメッシュ タイル木の geometricError による切替（HLOD） 多数フィーチャを 1 タイルへ結合してドローコール削減。広域メッシュを階層化すれば高速。 全バージョン対応（1.0 の標準形式）
.i3dm 街路樹・電柱・センサ等「同一モデルの多数配置」 同上（インスタンスの集合をタイル分割） GPU インスタンシングで 1 モデルを繰返し描画するため最速級。配置だけを変えるデータでは、b3dm に個別結合するより大幅に軽い。
.pnts 点群（LAS/LAZ/XYZ/PLY 由来） オクツリー分割＋遠景の点間引き（プログレッシブ表示） 遠景は粗い点疎表示・近景は高密度に自動遷移。数千万点規模でも初期表示が速い。1.1 では glb 化が推奨。
.glb（1.1） メッシュ・インスタンス・点群すべて 同上（タイル木は共通） 転送・デコード面で総合的に最速。Draco/meshopt 圧縮・KTX2 圧縮テクスチャが使え、1.0 コンテナより小さく軽い。新規作成はこれが第一選択。 CesiumJS 1.107 以降（1.1 対応）

Cesium 対応について: 上記 4 形式はすべて CesiumJS で描画できます。 ただし .glb コンテンツ（3D Tiles 1.1）は CesiumJS 1.107 以降が必要です。 1.107 未満の古い CesiumJS や、three.js 系ローダ等の Cesium 以外のビューアでは 1.0 形式（.b3dm / .i3dm / .pnts）のみ対応の場合があるため、 最大互換性が必要なら --tilesVersion 1.0 / --version 1.0 で 1.0 出力を選んでください。

テクスチャ・マテリアルの再現性: .b3dm の中身も実は glTF（コンテナに包んだだけ）なので、 テクスチャ・PBR マテリアルの再現性は b3dm と glb で同格です。 glb はさらに KTX2（Basis Universal）/ WebP 等の圧縮テクスチャ拡張が使えるため、 同等の見た目を保ったまま軽量化できる点で有利です。 一方 .pnts にはテクスチャが存在せず頂点色のみのため、 フォトグラメトリ等のテクスチャ付きモデルは必ずメッシュ系（b3dm / glb）ルートを選んでください。 実際の再現性はコンバータ側の解釈にも依存します（mago/Assimp のマテリアル解釈、 OBJ+MTL 等のテクスチャ参照は入力と同一ディレクトリへの配置が必須）。 --quantize や Draco 圧縮はジオメトリの圧縮でありテクスチャは維持されます。

2-3. KASUGAI Canvas のエンジン別対応

本ツールの出力を表示する KASUGAI Canvas 側のエンジン対応は次のとおりです （Canvas が読む .kasc の 3dtiles: レイヤとして供給する場合）。

Canvas エンジン3D Tiles 表示方式対応形式
Cesium（メインエンジン） Cesium3DTileset ネイティブ（同梱 CesiumJS 1.147.0） b3dm / i3dm / pnts / glb すべて対応。1.1 出力もそのまま表示可
MapLibre deck.gl Tile3DLayer（deck.gl 9.4 + loaders.gl、3dtiles 含有時のみ CDN 遅延ロード） b3dm / i3dm / pnts / glb（loaders.gl 経由）。2D マップ上に 3D タイルを重畳

まとめ: Canvas での表示対象は GSI Maps 以外の全エンジンです。 メインの Cesium は 1.1（glb）を含む全形式をネイティブ描画でき、 MapLibre / OpenLayers / Leaflet は deck.gl 経由で同じタイルセットを 2D マップ上に重畳表示します。 出力形式を選ぶ際は CesiumJS 1.147 環境なら 1.1（glb）、他エンジン併用や古い環境も考慮するなら 1.0（b3dm/pnts）が無難です。

3. 入力可能形式（理論対応表）

3-1. 自動変換のルーティング

「データ変換 → 自動変換」タブでは、出力形式 × 入力拡張子からエンジンを自動選択します。 3D Tiles 系の対応は次のとおりです。

出力形式入力可能拡張子使用エンジン
b3dm shp / geojson / json / gpkg / kml / gml / xml / obj / fbx / 3ds / ase / dae / gltf / glb / stl / ply / x3d / 3mf / ifc / lxo / lwo / lws / x mago-3d-tiler
i3dm shp / geojson / json / gpkg / kml mago-3d-tiler（要 --instance。追加オプションに指定）
pnts las / laz → gocesiumtiler、xyz / ply のみ → Py3DTiles gocesiumtiler / Py3DTiles
3dtiles-1-1-glb 既定・推奨 b3dm と同一 ＋ las / laz（点群は mago で pnts 生成後 1.1 へ upgrade し glb 化） mago + 3d-tiles-tools
b3dm（PostGIS） PostGIS テーブル（3D ジオメトリ） pg2b3dm（個別コンバータから）

コンバータ選択の優先順位

  1. 第1キーは output_format（UI の出力形式選択）。 b3dm / i3dm は mago 固定、3dtiles-1-1-glb は mago + 3d-tiles-tools パイプライン固定です。エンジンが複数あり得るのは pnts のみです。
  2. pnts 内の優先順位: 入力ディレクトリの拡張子を走査し、 .las / .laz が1つでもあれば gocesiumtiler を優先します （LAS 専用・オクツリー高速・サブサンプリング対応）。 las/laz がなく .xyz / .ply のみの場合だけ Py3DTiles へ分岐します。
  3. 入力形式の決定: API の input_format 明示指定が最優先。 未指定時はディレクトリを走査して自動検出します（mago 本体の判定順と同じ KML 優先 → 先頭一致で決定）。
  4. pg2b3dm は自動ルーティングの対象外です （PostGIS 接続情報が必須のため、個別コンバータタブからのみ実行します）。
注意: pnts で .las と .xyz が混在する入力を 自動変換すると gocesiumtiler が選択され、xyz / ply ファイルは処理されません。 混在する場合は形式ごとに分けて変換するか、Py3DTiles ルートを個別に実行してください。 また mago も las/laz → pnts を処理できますが、自動変換では点群専用の gocesiumtiler を優先しています （mago ルートは個別コンバータタブから利用可能）。

3-3. 点群（pnts）の入力とエンジン分担

入力gocesiumtilerPy3DTilesmago
.las / .laz○（自動変換の既定）○（.laz は lastools 必要）○

自動変換で pnts を選んだ場合、入力ディレクトリ内の拡張子を走査し、 las/laz があれば gocesiumtiler、xyz/ply のみなら Py3DTiles を選択します。 .ply はエンジンによって意味が異なる点に注意してください（mago ではメッシュ → b3dm、 Py3DTiles では点群 → pnts）。

3-4. i3dm の入力要件

i3dm（インスタンスタイル）は GIS の点フィーチャ + インスタンスモデルの組合せです。 入力として shp / geojson / json / gpkg / kml を受け付け、インスタンスモデルは --instance オプションで指定します（既定 {出力}/instance.dae）。 自動変換では「追加オプション」に --instance path/to/model.dae と記述してください。 向き・大きさ・密度は属性列で制御します（--headingColumn / --scaleColumn / --densityColumn）。

3-5. pg2b3dm の入力

PostGIS データベースの 3D ジオメトリ列を直接 b3dm 化します。ファイル入力ではなく --connection + --table（+ 任意で --query で絞り込み）を指定します。

4-7. 前処理で品質を上げる

変換前の前処理で出力品質を改善できます。「前処理」タブから利用します。

  • glTF 最適化（gltf-pipeline）: Draco 圧縮等で glb/b3dm 内 glTF を軽量化。テクスチャ圧縮・メッシュ最適化。
  • GDAL/PDAL: 再投影・座標系統一・点群フィルタで入力品質を整える。
  • XY 反転（laspy）: 軸順が逆の LAS/LAZ を変換前に修正。
  • OBJ 表面処理: 法線・面の向き・UV の反転で表示崩れを修正。

5. 既知の制限・注意事項

  • mago の --absoluteAltitude は 1.15.4 で実質無効: 高度列解決の内部処理に上書きされるため、本ツールでは z_offset と absolute_altitude を数値加算して --zOffset で渡すワークアラウンドを行います （非数値の場合は選択値をそのまま透過）。
  • mago 既定は 1.1 出力: --outputType b3dm でも asset.version 1.1 + .glb になります。1.0 の .b3dm が 必要なら追加オプションに --tilesVersion 1.0。
  • 無効な --inputType はエラーにならない: KML へ静かにフォールバックして後段で失敗するため、ツール側で有効トークンへ正規化しています。 手動で CLI を呼ぶ際も gltf/glb のような複合値は使わないでください。
  • .ply の二義性: mago ではメッシュ（→b3dm）、Py3DTiles では点群（→pnts）。 点群 PLY を b3dm にしたい場合は意図的に mago ルートを選んでください。
  • i3dm は --instance 必須: 未指定時は {出力}/instance.dae を探します。モデルを置くか追加オプションで指定してください。
  • pnts は 1.1 では非推奨: 3D Tiles 1.1 では点群も glb コンテンツが推奨です。 pnts（1.0）で生成後、3d-tiles-tools の upgrade（「3D Tiles 1.1」ルート）で 1.1 化できます。
  • mago が収集しない拡張子: .kmz / .igml / .citygml は 対象外です（.gml/.xml として citygml/indoorgml で扱います）。

6. 確認・診断

  • 生成物のバージョンは tileset.json の asset.version、コンテンツは content.uri（.b3dm/.glb/.pnts）で確認。
  • 「データ変換 → 関連システム」タブで各ツールの検出状態と対応拡張子を確認できます。
  • POST /api/inspect で生成タイルセットの構造を診断する機能があります（診断/プレビュー）。
  • ジョブの実行ログには実際に渡された CLI 引数が記録されるため、意図したオプションが反映されたか確認できます。
